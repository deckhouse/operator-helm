# AGENTS.md

operator-helm is a Deckhouse module (`module.yaml`, namespace `d8-operator-helm`) that deploys
Helm applications declaratively. User-facing CRDs in the `helm.deckhouse.io` group are reconciled
into internal Flux objects (API groups renamed to `*.internal.operator-helm.deckhouse.io`) that
vendored Flux controllers process behind a rewriting proxy.

Run every `task` command with `TASK_X_REMOTE_TASKFILES=1` — the root Taskfile includes remote
taskfiles from werf/common-ci and task refuses them otherwise. Non-interactive runs also need
`task --yes` to accept the remote taskfile trust prompt. Formatting/linting of `crds/*.yaml`
(prettier) and `task lint:doc-ru` run in containers, so docker is required for
`task format`, `task lint`, and `task generate:api`.

## Repository layout

- `api/` — standalone Go module: `v1alpha1/` types, generated clientset/informers/listers in
  `client/generated/`, name-derivation helpers in `naming/`. Regenerate with `task generate:api`.
- `crds/` — CRD manifests. English `*.yaml` are **generated** from `api/v1alpha1` markers
  (never hand-edit); `doc-ru-*.yaml` are hand-maintained Russian translations; `embedded/`
  holds the renamed upstream Flux CRDs (generated, excluded from translation).
- `images/` — one directory per container image, each Go image is its own Go module:
  - `operator-helm-controller/` — the main controller. The reconcile logic is shared: one
    reconciler per role in `internal/reconcile/{release,repository}`; everything that differs
    between kinds lives in `internal/adapter/` behind the interfaces of `internal/contract/`;
    `internal/controller/<kind>/` is only wiring (controller + mapper). Other packages:
    `webhook/` (admission), `catalog/`+`reposync/`+`chartsource/` (chart catalog sync),
    `internalobj/` (internal Flux objects), `rbac/` (the identity a release is applied with),
    `claim/` (at most one HelmClusterAddon per repository/chart pair, via a Lease).
  - `chart-values-controller/` — HTTP service (`POST /v1/chart-values`) returning chart values
    to the Deckhouse console.
  - `hooks/` — addon-operator module hooks (`pkg/hooks/`: TLS certificates, finalizer cleanup,
    namespace deletion).
  - `kube-api-rewriter/` — proxy that renames Flux API groups, adapted from Deckhouse's
    kube-api-rewriter; this repo's rule table lives in `pkg/operatornelm/`. Note:
    `task test:unit` covers only `pkg/operatornelm`, not the rewriter core.
  - `helm-controller/`, `source-controller/` — upstream Flux images, build config only
    (`werf.inc.yaml`); versions pinned in `build/components/versions.yml` and checked by
    `task check-flux-tags`.
- `templates/`, `charts/`, `Chart.yaml`, `openapi/` — the module's Helm chart and its
  config-values schema (standard Deckhouse module layout).
- `tests/e2e/` — Ginkgo e2e suite, standalone Go module.
- `tools/` — `internalcrds/` (regenerates `crds/embedded/` from upstream Flux),
  `validation/` (PR diff checks; not wired into CI and currently broken — don't rely on it).
- `docs/` — user documentation, `*.md` / `*.ru.md` pairs. Documentation changes go in
  separate PRs, not mixed with code changes. `RELEASE_NOTES*.md` are generated by the release
  workflows (`hack/chlog.py` from `CHANGELOG/`) — never edit by hand.
- `.werf/`, `werf.yaml` — module image build (`task build`, requires werf).

## Domain model

All user-facing kinds live in `helm.deckhouse.io/v1alpha1` (`api/v1alpha1/`). Two families:

- **Cluster addons** (cluster-scoped, for platform admins):
  `HelmClusterAddonRepository` → catalog of `HelmClusterAddonChart` → `HelmClusterAddon`.
  An addon is applied with cluster-wide rights into `spec.namespace` (system namespaces are
  forbidden), and at most one addon may use a given repository/chart pair.
- **Namespaced applications** (for namespace users): `HelmApplication` deploys a release into
  its own namespace under a ServiceAccount with namespace-admin rights. Charts come either
  from a namespaced `HelmApplicationRepository` (catalog: namespaced `HelmApplicationChart`)
  or from a shared cluster-scoped `HelmClusterApplicationRepository` (catalog: cluster-scoped
  `HelmClusterApplicationChart`).

Chart catalog objects are operator-owned (`heritage: deckhouse`), rebuilt by repository sync
and immutable to users. Chart object names are derived from repository + chart name via
`api/naming`. Each repository/release maps to internal Flux objects in `d8-operator-helm`
(group, kind, and resource are renamed, e.g. `InternalNelmOperatorHelmRelease` in
`helm.internal.operator-helm.deckhouse.io`), reconciled by the vendored
source-/helm-controller through kube-api-rewriter.

## Tests

### Unit

Standard Go tests (stdlib `testing`, controller-runtime fake client in the controller,
module-sdk mocks in hooks; no ginkgo) next to the code in every module. `task test:unit` runs all modules;
per module: `task api:test:unit`, `task hooks:test:unit`, `task operator-helm-controller:test:unit`,
`task chart-values-controller:test:unit`, `task internalcrds:test:unit`, plus
`task test:rewrite-rules` (checks `pkg/operatornelm` rules against `crds/embedded/`).

### E2E (`tests/e2e/`)

Single Ginkgo suite (`e2e_test.go`) that blank-imports per-resource spec packages:
`helmapplication/`, `helmapplicationrepository/`, `helmclusteraddon/`,
`helmclusteraddonrepository/`. Shared plumbing in `internal/`:

- `framework/` — config (env `E2E_*`), cluster client, cleanup, failure dumps, timeouts;
- `util/` — shared helpers (delete/update and condition waiters per kind, namespaces, pods,
  ModuleConfig handling);
- `controller/` — streams controller logs and counts restarts for the whole run.

The suite enables the module once in `SynchronizedBeforeSuite` and at teardown asserts no
controller errors or restarts; expected log noise is filtered in `default_config.yaml`.
New specs follow this shape: a spec file per scenario in the resource's package, helpers in
`internal/util`, never a per-spec module enable.

### Running e2e locally

The full guide (kind setup, the dev loop, deploying a PR build) is `tests/e2e/README.md`.
The short version: `task test:e2e:setup` brings up a kind cluster with Deckhouse, then the
`dev:*` tasks drive the loop — `task dev:build` publishes the working tree via
`hack/dkp-build-module.sh`, `task dev:test:e2e:env` resolves the digest and writes
`tests/e2e/.env` (gitignored, picked up by every e2e run through the root Taskfile's
dotenv), `task dev:test:e2e` chains build + env + tests. Each input resolves as: explicit
var (`DEV_REGISTRY`/`DEV_TAG`) > value recorded in `.env` > CI-like default (shared dev
registry + `pr<N>` tag; `dev:build` never defaults the registry). `E2E_MODULE_DIGEST` is
mandatory for the suite; hand-written `.env` entries survive regeneration.

## CRD and docs translation

- English CRD descriptions live in the Go type comments/markers in `api/v1alpha1`;
  `task generate:api` regenerates `crds/*.yaml`. CI fails if generated files are stale.
- Every `crds/<name>.yaml` has a hand-written `crds/doc-ru-<name>.yaml`: the same YAML
  structure, but containing only translated schema `description` fields (printer-column
  descriptions are deliberately left out). Same pattern for
  `openapi/config-values.yaml` ↔ `openapi/doc-ru-config-values.yaml` and
  `docs/*.md` ↔ `docs/*.ru.md` — always change both sides of a pair in the same PR.
- Structural en↔ru mismatch in `crds/` is caught by `task lint:doc-ru` (needs docker,
  part of `task lint`, runs in CI).
- `crds/embedded/` is not translated; regenerate it with `task generate:internal-crds` after
  bumping Flux versions in `build/components/versions.yml` (keep `images/*/werf.inc.yaml`
  pins in sync — `task check-flux-tags`).

## Commits, branches, PRs

See CONTRIBUTING.md. Summary:

- Conventional commits: `<type>(<scope>): <subject>`. Types: `feat`, `fix`, `security`,
  `refactor`, `docs`, `test`, `chore`, `internal` (developer-only, excluded from the
  changelog). Subject: imperative, lowercase, no trailing dot. Scopes in use: `api`, `core`,
  `ci`, `docs`, `module`, `changelog`, `release`.
- Sign off every commit (DCO): `git commit -s`.
- Branch names: `<type>/<scope>/<short-description>` (kebab-case, top-level scope only).
- PR title follows the commit header format. PRs are squash-merged, so the PR title becomes
  the commit subject that git-cliff (`cliff.toml`) parses into the changelog — get it right.
  `feat` bumps minor, `internal` is excluded.
- CONTRIBUTING.md also asks for a ` ```changes ` block in the PR body
  (`section`, `type`, `summary`, optional `impact_level`/`impact`).

## Everyday commands

```shell
task deps:install:all     # gci, gofumpt, golangci-lint, ginkgo
task format               # formatters in all modules
task lint                 # golangci-lint in all modules + doc-ru linter
task test:unit
task generate:api         # after changing api/v1alpha1
task build                # werf build of module images
```
